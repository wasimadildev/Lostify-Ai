Lostify AI — Complete Technical Documentation

A lost-and-found matching engine. A user reports a lost pet, person, or item with a photo and/or a text description; the system finds and ranks the most similar stored cases with an explainable score. This document explains every technology, why it is used, its features, and exactly how it works under the hood — including the SQLite persistence layer and the live React + Tailwind frontend.

01System Architecture

The system is a pipeline: it converts free-form input (an image, a sentence, or both) into a mathematical vector, searches a pre-built vector index, then applies business rules (metadata filtering) and a human-readable ranking. Everything is built so a React frontend can drive the same FastAPI service later.

The one-line summary Images and text live in the same 512-dimension space. Similarity = distance in that space. FAISS finds the nearest stored vectors fast. Metadata + weights turn similarity into a decision. New reports are embedded on the spot and appended to the live index, so they become searchable immediately — no rebuild, no restart.
Visual architecture diagram An interactive, colour-coded version of this pipeline (online + offline lanes, every component tagged with its file) lives at architecture.html.

Key design decisions:

  • One combined embedding, one FAISS search — we do not search twice and add scores; we fuse image + text into a single vector, so the candidate set already reflects both modalities.
  • Wide net, then filter — FAISS returns 20 candidates; metadata filtering (pets vs persons vs items) removes wrong-type matches; ranking orders the survivors.
  • Explainable scores — visual, text, location, and final scores are returned separately so a user (or an examiner) sees why a case matched.
  • Precomputation — all 44 case images are embedded once at build time. At request time the model runs only on the query, and the search itself is a millisecond.

2.2 PyTorch

What it is: an open-source deep-learning framework (Meta/now Linux Foundation) that runs tensor operations on CPU or GPU with automatic differentiation.

Why we use it: Hugging Face Transformers is built on PyTorch. We never write a network ourselves — we rely on PyTorch to execute the CLIP model's forward pass.

  • Tensors: multi-dimensional arrays that can live on GPU devices. CLIP tensors here are shapes like 1x3x224x224 (image) and 1x77 (text tokens).
  • torch.no_grad(): disables gradient tracking during inference — saves memory and speeds up the forward pass, producing our embeddings.
  • Device handling: "cuda" if torch.cuda.is_available() else "cpu". This runs on CPU today (Apple Mac, no NVIDIA GPU) and automatically upgrades if a GPU ever exists.
# engine.py — the actual inference call
with torch.no_grad():
    output = self.model.vision_model(**inputs).pooler_output   # 1×768 tok
    output = self.model.visual_projection(output)              # 1×512 vec

2.3 Hugging Face Transformers + CLIP

What it is: an open-source library that gives one-line downloads and execution of thousands of pretrained transformer models through a consistent API.

What CLIP is

CLIP (Contrastive Language–Image Pre-training) was introduced by OpenAI in 2021 in the paper "Learning Transferable Visual Models From Natural Language Supervision". It trains two encoders at the same time:

Vision tower

ViT-B/32

A Vision Transformer: the 224×224 image is cut into 7×7 = 49 patches of 32×32 pixels, embedded, then processed by 12 transformer layers. Output projected to 512 dims.

Text tower

Transformer

A 12-layer text transformer. Text is lowercased, byte-pair-tokenized, padded/truncated to 77 tokens. Final token projected to 512 dims.

Objective

Contrastive loss

Train on 400M image–text pairs: pull matching pairs together in the 512-D space, push non-matching apart (InfoNCE loss).

Why we use CLIP (not a cnn, not YOLO)

  • One space for images AND text. This is the entire trick: an image of a white Persian cat and the sentence "white persian cat" end up near each other. Classic classifiers can't compare a photo to a sentence.
  • Zero-shot. We can describe a lost item in plain words and it matches the right image without ever training a classifier on our categories.
  • 512-D shared space. Both modalities are projected to the same 512-dims, so one vector can represent the user's whole report (see §2.4).

How the embedding is computed (under the hood)

  1. CLIPProcessor resizes the image to 224×224, converts to RGB, and normalises pixels with CLIP's ImageNet statistics. For text it tokenises with the CLIP BPE tokenizer.
  2. The vision tower gives a pooler_output of 768 dims; visual_projection matrix maps it to 512.
  3. The text tower gives a pooler_output of 512 dims (already 512); text_projection keeps it 512.
  4. We L2-normalize the vector so its length is 1. Then cosine similarity = inner product, which is exactly what our FAISS index computes.
# The whole embedding recipe, from engine.py
inputs    = self.processor(images=image, return_tensors="pt").to(self.device)
output    = self.model.vision_model(**inputs).pooler_output
output    = self.model.visual_projection(output)
output    = output / output.norm(dim=-1, keepdim=True)      # unit length
return output.cpu().numpy().astype(np.float32).flatten()   # 512-D

2.4 NumPy

What it is: the fundamental package for numerical arrays in Python. Under the hood it wraps highly optimised C/Fortran SIMD code; vectorised operations avoid slow Python loops.

  • Embedding fusion: np.asarray(emb, dtype=np.float32) turns model output into arrays.
  • L2 normalization: vector / np.linalg.norm(vector) — the length-1 guarantee that makes cosine = inner product (crucial for FAISS, see §2.5).
  • DP3 storage format: all 44 embeddings are saved as .npy files, the canonical NumPy format, then loaded by the FAISS build script.

2.5 FAISS

What it is: (FAcebook AI Similarity Search) a library for efficient similarity search over dense vectors. It stores vectors in a flat array and answers nearest-neighbour queries.

The index we use: IndexFlatIP

SettingValueMeaning
TypeIndexFlatIPInner Product — exact (brute-force) search, no approximation
Dimension512Matches CLIP's embedding size
Vectors44 (index.ntotal)One per case, stored as float32
Distance metriccosine similarityBecause every vector is L2-normalized, inner product = cosine
Persistencefaiss.write_index / read_indexIndex is built once and loaded at startup
Why "inner product" = "cosine similarity" Cosine similarity compares direction: cos(θ) = (a·b) / (‖a‖·‖b‖). If we force both vectors to length 1 (L2-normalize), the denominator is always 1, so cos(θ) = a·b — a single dot product. FAISS's IndexFlatIP computes exactly that.

How index.search(query, k) works

  1. FAISS reshapes the query to (1, 512) and re-normalises it (faiss.normalize_L2).
  2. It computes the inner product of the query with every stored vector — for 44 vectors that is a trivially fast 44 multiply-adds (≈ 0.004 ms measured).
  3. It returns two arrays: indices (positions in the index) and similarities (scores), sorted descending.
  4. We map index positions → case IDs using the parallel file embeddings/case_names.txt (line i is the case at position i).
# store.py — the thin FAISS wrapper
query = np.asarray(query_emb, dtype=np.float32).reshape(1, -1)
faiss.normalize_L2(query)
similarities, indices = self.index.search(query, top_k)          # brute-force dot
results = [(self.case_names[idx], float(sim)) for idx, sim in zip(indices[0], similarities[0])]
return sorted(results, key=lambda x: x[1], reverse=True)

Why not just numpy dot? FAISS is the industry standard for this job and is free for brute-force search. When the dataset grows to thousands or millions of cases, the same API accepts IndexIVFFlat/IndexHNSW or GPU indexes without changing our code.

2.6 Pillow (PIL)

What it is: the default Python image library. Why: CLIP needs raw pixel tensors, and uploaded/downloaded files arrive as JPEG/PNG bytes.

  • Image.open(BytesIO(bytes)).convert("RGB") decodes uploads in memory — no temp files.
  • convert("RGB") guarantees a 3-channel image, so the processor never fails on RGBA/greyscale files.
  • Used in engine.py for queries and in generate_embeddings.py for building case vectors.

Why FastAPI specifically

  • Type-driven. Parameters are declared with types (UploadFile, Form, int, float). Validation errors become clean 400 responses automatically.
  • Async friendly. await image.read() reads uploads without blocking other requests.

How an HTTP request flows

  1. Browser/React sends multipart/form-data (image file + text fields).
  2. Uvicorn accepts the connection; python-multipart splits the body into parts.
  3. FastAPI validates and injects them as typed parameters into the route function.
  4. The route calls engine.search(...) synchronously (CPU-bound; Python releases compute to C), measures time, and returns JSON.
  5. FastAPI serialises the Python dict to JSON; Uvicorn streams the HTTP response.

2.8 SQLite (the persistence layer)

What it is: a self-contained, file-based relational database that ships inside Python's standard library (import sqlite3 — no server, no extra dependency). The whole database lives in one file, learning/Week-03/lostify.db.

Why we use it: the search index (index.index) is the fast storage but it only keeps vectors and case IDs. To answer "list every report" and to remember who submitted what, we add a friendly, queryable store. SQLite is the smallest thing that does that, is transactional (crash-safe), and needs nothing to be installed.

2.8.2 Seeding and lifecycle

  1. init_db() runs at API startup and creates the table if it does not exist.
  2. seed_from_metadata() reads the 44 records from metadata.json and inserts them with source='dataset' (idempotent — it skips case_ids that already exist).
  3. insert_report() adds a user submission with source='user' in the same transaction that closes the connection (autocommit).
  4. next_case_id() picks the next free ID per type by counting existing rows, so new reports naturally continue the dataset prefixes (PETS-15, PERS-11, ITEMS-21…).
# db.py — every query goes through the same tiny helper
def insert_report(record, db_path=DB_PATH):
    conn = connect(db_path)
    try:
        cur = conn.execute(
            "INSERT INTO reports (case_id, case_type, category, title, description,"
            " location, latitude, longitude, date_lost, status, source)"
            " VALUES (?,?,?,?,?,?,?,?,?,?,?)",
            (record["case_id"], record["case_type"], record["category"],
             record["title"], record["description"], record["location"],
             record["latitude"], record["longitude"], record["date_lost"],
             record["status"], record.get("source", "dataset")),
        )
        conn.commit()
        return cur.lastrowid
    finally: conn.close()
# Note: every helper takes db_path=DB_PATH so tests can point at a temp file.

03Search Pipeline, Step by Step

This is the heart of the system (engine.py → CLIPEngine.search). Every step maps to one concrete function you can read in the code.

#StepFunctionOutput
1Parse inputsCLIPEngine.searchhas_image, has_text
2Embed the queryimage_embedding_from_bytes / text_embeddingtwo 512-D vectors
3Fuse modalitiescombine_embeddingsone 512-D vector, length 1
4Retrieve candidatesstore.nearest(combined, 20)top-20 (case_id, similarity)
5Build score maps_similarity_mapper-case visual/text scores
6Filterfilter_candidatesonly matching type/category/status
7Rankrank_candidatessorted list with final_score
8Sliceranked[:top_k]top 5 by default

Step 3 in detail — why multimodal fusion works

Both CLIP encoders output vectors in the same 512-D space, so a weighted sum is meaningful:

combined = 0.7 × image_embedding + 0.3 × text_embedding
combined = combined / ‖combined‖     # back to unit length

The weights are normalised inside combine_embeddings (so 0.9/0.3 is treated as 0.75/0.25) and fully confused when only one modality exists: image-only queries search with just the image vector, text-only with just the text vector.

Why Step 5 needs a second full-index scan The candidates come from the combined vector, but we want separate visual_score and text_score per case. _similarity_map runs the raw image vector and the raw text vector against the full 44-vector index once each. That is why scores are precise and explainable even though the candidate pool came from a fused query.

05The Services (how the code is organised)

The pipeline is split into four small, testable services under services/, plus the SQLite layer in db.py. Each name says what it does; each is unit-tested (41 tests, < 0.1 s).

5.1 store.py — CaseStore

Loads the three runtime artifacts once and keeps them in sync:

  • faiss.read_index("embeddings/index.index") — the 44-vector index
  • embeddings/case_names.txt — position → case_id mapping
  • metadata.json — the case records

Exposes search() (raw FAISS), nearest() (returns (case_id, sim) pairs sorted), and — new this week — add_case(). Because the index can never be mistaken for the metadata order, the mapping file is the only alignment guarantee.

5.1.1 add_case() — grow the index live

Called by POST /reports. Input: a brand-new case_id, its 512-D CLIP embedding, and its metadata record. It appends the vector to the FAISS index and persists all three artifacts so the case survives a restart:

# services/store.py — add_case()
vector = np.asarray(embedding, dtype=np.float32).reshape(1, -1)
faiss.normalize_L2(vector)                    # keep cosine = inner product
self.index.add(vector)                        # ntotal 44 → 45

if case_id not in self.case_names: self.case_names.append(case_id)
self.metadata[case_id] = metadata

faiss.write_index(self.index, self.index_path)          # index.index
with open(self.names_path, "w") as f:  f.write("\n".join(self.case_names))  # names
with open(self.metadata_path, "w") as f: json.dump(self.metadata, f)      # metadata.json
A bug we caught (and why the lesson is in the docs) An early version of add_case() took default file paths. The unit tests called it without overriding those defaults, so test vectors were persisted into the real index.index / metadata.json and the 44-case dataset collapsed to two records. Recovery was a re-run of create_metadata.py + build_faiss_index.py (the .npy vectors and images were never touched). The fix: add_case() now writes to the same paths the store was loaded from, so tests can never hit production data. The regression tests tests/test_store_add_case.py now verify both persistence and that the production files stay untouched.

5.2 filtering_service.py — filter_candidates

Runs AFTER FAISS but BEFORE ranking. Applies simple, strict filters so a "lost white cat" never returns a white dog, shirt, or car:

if query_type:  keep cases where case_type == query_type   # lost_pet / lost_item / lost_person
if category:   keep cases where category == category     # cat, dog, bicycle, ... (case-insensitive)
if status:     keep cases where status == status         # open / closed
Why filter after search and not before the query embedding Filtering is a decision, not a vector operation. Broad recall first (top 20), precision later (metadata equality). This keeps one FAISS index that works for every type.

5.3 multimodal_service.py — combine_embeddings

Fuses image + text into one vector (full logic in §3 Step 3). Handles all three cases (image only, text only, both) and raises ValueError for a zero vector or no inputs.

5.4 ranking_service.py — rank_candidates

Computes the weighted, explainable scores and sorts. Full formula in §6. It also contains the haversine_km and location_score helpers used for the location component.

5.5 engine.py — CLIPEngine (the conductor)

Not a "service" in the folder, but the integration point: one class that owns the model, the processor, and the store, and exposes search() (read path) and add_report() (write path). Every entry point shares it:

06Scoring & Ranking (why a case "matches")

6.1 The formula

final_score = (0.70 × visual_similarity
             + 0.20 × text_similarity
             + 0.10 × location_score)
                ÷ (sum of weights actually present)

Weights default to 0.70 / 0.20 / 0.10 but are renormalised over the active components. For a text-only query there is no visual component, so text (0.20) and location (0.10) are re-weighted to sum to 1.0 — the final score is always a true 0–1 blend, not an artificially deflated number.

ComponentSourceHow it is computed
visualimage (if provided)cosine similarity of the raw image vector vs each case, from a full-index scan
texttext (if provided)cosine similarity of the raw text vector vs each case
locationlocation field or lat/lonexact city match → 1.0, else haversine decay (see below)

6.2 The location component

location_score implements a simple "proximity bonus":

  • Exact city-name match (case-insensitive) → 1.0. E.g. query "Islamabad" and case "Islamabad".
  • Otherwise, if coordinates are known, compute the great-circle distance with the haversine formula and decay linearly from 1.0 at 0 km to 0.0 beyond 200 km: max(0, 1 − distance_km / 200).
  • No query location → the component is None and excluded from the final blend (weight goes back to visual/text).

RawalpindiIslamabad≈ 12 km0.94
LahoreIslamabad≈ 270 km0.0 (capped)
(none)any—None (excluded)

Query: text="lost white persian cat in Islamabad", query_type=lost_pet, returned PETS-01 at rank 1:

case_id      = PETS-01   White Persian Cat with Blue Collar

7.4 Honest reading of the results

  • Image mode is 100% because image queries are self-retrieval (an image finds itself) — it verifies the plumbing, not the AI.
  • Text mode is the real test. 89.7% Top-1. Two known misses: a toddler described only as "young toddler in bright yellow sweater" (PERS-07) and a generic water bottle (ITEMS-18). Both succeed as soon as the user adds a photo → this is the biggest argument for the combined image+text form.
  • Everything is reproducible. python evaluation/evaluate.py re-runs the 47 queries and rewrites results.json. Any change to data/weights/code is measured against the same set. That is the "measure before improving" loop for Week 04.

9.4 Upload + search — the exact React code

Upload is a form. On submit, build FormData and send it. Never send JSON when a file is involved.

import { useState } from "react";

function SearchPage() {
  const [image, setImage] = useState(null);   // File | null
  const [text, setText] = useState("");
  const [queryType, setQueryType] = useState("lost_pet");
  const [location, setLocation] = useState("");
  const [results, setResults] = useState([]);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState(null);

  async function handleSubmit(e) {
    e.preventDefault();
    if (!image && !text.trim()) { setError("Add a photo or a description."); return; }

    const fd = new FormData();                   // ← multipart/form-data
    if (image)  fd.append("image", image);
    if (text)   fd.append("text", text);
    fd.append("query_type", queryType);
    if (location) fd.append("location", location);
    fd.append("top_k", "5");

    setLoading(true); setError(null);
    try {
      const res = await fetch("http://localhost:8000/search", { method: "POST", body: fd });
      const data = await res.json();
      if (!res.ok) { setError(data.detail); return; }
      setResults(data.results);                 // top 5, already ranked
    } catch {
      setError("Could not reach the AI service.");
    } finally { setLoading(false); }
  }
  /* JSX in §9.5 renders `results` with Tailwind */
}

9.6 The score-bar component

function ScoreBars({ scores }) {
  const rows = [
    { label: "Match",    value: scores.final },
    { label: "Visual",   value: scores.visual },
    { label: "Text",     value: scores.text },
    { label: "Location", value: scores.location },
  ].filter(r => r.value != null);   // null = that component wasn't used

  return (
    <div className="space-y-1.5">
      {rows.map(r => (
        <div key={r.label}>
          <div className="flex justify-between text-xs text-slate-500">
            <span>{r.label}</span>
            <span className="font-mono">{r.value.toFixed(2)}</span>
          </div>
          <div className="h-1.5 bg-slate-100 rounded-full overflow-hidden">
            <div className="h-full rounded-full bg-blue-600 transition-all"
                 style={{ width: `${Math.round(r.value * 100)}%` }} />
          </div>
        </div>
      ))}
    </div>
  );
}

10Glossary

Embedding
A fixed-size vector of numbers that represents the meaning of an image or text. Here: 512 numbers from CLIP.
CLIP
OpenAI's Contrastive Language–Image Pretraining model; two encoders trained so matching image/text pairs sit close together in one space.
ViT-B/32
A Vision Transformer variant: "Base" size, image split into 32×32 pixel patches. It is the vision half of our CLIP model.
Patch
A 32×32 px tile of the 224×224 input image; 7×7 = 49 patches feed the transformer.
Contrastive objective / InfoNCE
Training loss that maximises similarity between correct pairs and minimises it for incorrect ones in each batch.
Cosine similarity
A measure of direction similarity between vectors, 0..1 here.
L2 normalisation
Dividing a vector by its length so it has magnitude 1; this makes cosine similarity equal to a simple dot product.
Inner product (dot product)
Σ aᵢ·bᵢ — what FAISS's IndexFlatIP computes.
FAISS
Facebook AI Similarity Search — library of vector indexes and search algorithms.
IndexFlatIP
FAISS's exact brute-force inner-product index. "Flat" = no clustering/compression.
index.ntotal
Number of vectors stored in a FAISS index (here 44).
Candidate pool
The broad set FAISS returns before filtering — we ask for 20 candidates (candidate_k).
Metadata
Structured data about each case: type, category, location, date, status — served alongside the vector.
Multimodal
Using two or more input types together — here image + text in one search.
Zero-shot
Working on categories never seen in training, via natural-language descriptions.
Haversine formula
Great-circle distance between two coordinates on a sphere, in km.
MRR
Mean Reciprocal Rank — average of 1/rank of the expected result over queries.
Hit@k / Top-k accuracy
Fraction of queries where the correct case appears in the top k results.
FastAPI
Python web framework; declarative routes, auto-validation, automatic OpenAPI/Swagger docs.
Uvicorn
ASGI server that runs the FastAPI application.
multipart/form-data
The HTTP content type for file uploads + form fields; required by POST /search.
CORS
Cross-Origin Resource Sharing — browser security rule preventing a page on one origin from calling another without server permission.
FormData
The browser API for building multipart bodies to send files to our backend.
KMP_DUPLICATE_LIB_OK
macOS env var workaround because `faiss-cpu` and `torch` both link an OpenMP runtime.
SQLite
A file-based relational database that ships inside Python (import sqlite3). Here it stores every report in lostify.db — the 44 seeded cases plus user submissions.
lostify.db
The single SQLite file holding the reports table; created and seeded automatically at API startup.
Seeding
Inserting the initial 44 dataset records from metadata.json into SQLite (seed_from_metadata()), skipping ids that already exist so it can run repeatedly.
Transaction / commit
A unit of database work that either fully succeeds or is rolled back — sqlite3 commits on conn.commit(), keeping rows crash-safe.
source column
'dataset' vs 'user' — how the DB distinguishes seeded cases from live submissions; the frontend turns 'user' into a "New report" badge.
add_case() (live append)
Writes a new vector into the running FAISS index at request time and persists index/names/metadata — the opposite of an offline rebuild.
Offline rebuild vs online append
Rebuilding re-runs build_faiss_index.py over all .npy files (safe recovery); online append adds one case immediately (what POST /reports uses).
case_id
The business key shared by metadata, the FAISS names file, and the reports table (PETS-01…, PERS-11…, ITEMS-21…).
